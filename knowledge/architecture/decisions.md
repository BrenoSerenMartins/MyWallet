# Architecture decisions

- Use `knowledge/` as the project knowledge base; no Obsidian vault was found during initialization.
- Prefer simple, explicit implementations. Introduce abstractions only for existing duplication or real architectural boundaries.
- Start with a responsive PWA and manual statement uploads, as selected by the user. Reading other applications' notifications is outside the initial scope.
- Launch for personal use while accommodating future separate user accounts with isolated financial data. Hosting, authentication, synchronization, and household sharing are not selected or implied by this requirement.
- The user subsequently selected Supabase hosted PostgreSQL and requested CLI initialization and project linking. Keep credentials in ignored local configuration; do not include database credentials in the PWA.
- Each institution has its own statement mapper into a shared semantic financial model. Separate source extraction, institution interpretation, import validation, and persistence. Do not use bank-specific field names as the app's financial model. See `statement-imports.md` for terminology and verified Mercado Pago sample constraints.
- Product scope and release phases are recorded in `knowledge/domains/personal-finance.md`. Proposed additions are distinguished from user-requested capabilities.
- The user requested an immersive fintech/banking visual direction with theme switching. Proposed tokens and interaction rules are in `design-system.md`.
- The user requested a complete design/infrastructure/code execution plan using the sibling Tastly backend structure as a reference. `pilot-plan.md` records the inspected patterns, adapted Nest module boundaries, hosting implications, sequence, and acceptance criteria. Technical choices remain proposals until implementation, and no Tastly code or configuration is copied.
- Record future decisions here with their context and consequences.

- The user authorized pilot implementation. Use React/Vite plus a modular Nest API and Supabase Auth/PostgreSQL; only Auth is accessed directly from the browser. Public REST shapes generate frontend types from OpenAPI. TypeScript 5.9 satisfies the selected generator's peer contract.
- User provisioning confirmed that Supabase requires its root CA in this environment. Include the public Supabase Root 2021 CA (SHA-256 `807025AD50D4ED219D2C9C7D299C004F824EB00CF7F65AFEF607D07B72E6CAFA`) from the sibling's existing public CA file; verify TLS in every database client. No sibling credential was copied.
- The pilot's explicit migration runner owns `mywallet_migrations.applied`; do not combine it with CLI `db push` history. Hosting files are prepared but publication requires a configured hosting account and actual hosted acceptance checks.

- The user requested workspace selection through Trello-like cards. Workspaces remain private to their owner; shared membership is not introduced. Migration 002 preserves existing financial records under “Pessoal”. Financial tables require owner and workspace scope, with triple composite references to prohibit cross-space relationships. The API validates `X-Workspace-Id`; owner-only workspace listing/creation explicitly runs without financial scope. Frontend workspace switching replaces its financial QueryClient and screen state.

- The user confirmed separate cards and recurring-commitment screens and requested a complete product roadmap. Record features, dependencies, credit accounting/percentage semantics, wealth rules and staged acceptance in the existing personal-finance domain note. Prioritize card visibility/billing before recurring budgets and manual wealth/portfolio expansion; no future module or schema is scaffolded by planning.

- The user selected Render for hosting after the Cloudflare frontend deployment exposed the missing API runtime. Deploy the existing Docker image as one free Blueprint web service from main, serving React and Nest on one origin, with Supabase Auth/PostgreSQL retained. The separate Cloudflare frontend is optional and not required for this path. Migrations remain explicit local/release operations; only restricted runtime credentials enter the hosted service. No Render service has been created by the agent.

- The user supplied G-Base.xlsx from Downloads for inspiration. Inspect it read-only and capture its projected/actual/difference income, expense and contribution workflow in the existing domain roadmap. Propose a dedicated monthly planning increment that reads actuals from the existing ledger, with separate consumption/cash views and no duplicate card payments or contribution expenses. Do not copy personal amounts/workbook data into source, build a spreadsheet clone or assume implementation approval from the sample alone.

- The user authorized monthly planning and requested historical statement consultation during implementation. Implement category targets first, actuals from the canonical ledger, copy previews with optimistic versions and independent contribution intent. Add dedicated history status on import batches rather than an inclusion flag on every transaction; preserve normalized rows outside financial totals, and require explicit reconciliation before promotion into the ledger. Expand financial backup to version 2 for plans while retaining version 1 compatibility. Raw PDFs and consultation provenance remain outside the financial JSON backup, as documented.

- Expand Mercado Pago account-statement input to the user-provided PDF/CSV/XLSX exports. Keep format extraction separate from the institution mapper, share exact reconciliation, preserve source references as text and record format-specific mapper versions in the existing column. Reject unrelated report schemas instead of guessing their financial semantics. Retain reviewed duplicate checks across formats rather than making operation IDs globally unique. Source samples stay outside the repository; tests generate synthetic CSV/workbooks.

- Represent the requested hierarchy with category_groups and optional category.group_id, limited to two levels. Groups own name/type/color; financial records still reference leaf category IDs. Preserve old categories as ungrouped, allow category moves without rewriting transactions/plans, and scope uniqueness to each group/type. Composite owner/workspace/type foreign keys and RLS enforce boundaries. Financial backup version 3 preserves/remaps groups; accept versions 1/2 as ungrouped.
- Replace selectable proven duplicates with derived server-side locks. Reference+date+exact amount+source running balance identify source copies; references alone are not unique. Compare against original import provenance of active ledger rows, excluding the current batch and reversed rows. Recompute on review and under the existing account lock at confirmation, so overlapping drafts cannot create copies. Similar manual/no-provenance matches remain reviewable instead of silently discarding legitimate equal payments.

- Replace the virtual ungrouped section with real default groups per workspace/income-or-expense type. Migration 005 assigns existing null references without changing category IDs and provisions defaults for future workspaces via a narrowly scoped trusted trigger. Keep user-created Geral groups untouched by choosing a free default display name. Protected defaults cannot be renamed, unmarked, moved or deleted; a category trigger maps legacy null writes to the matching default during rollout.
- Group deletion is a reviewed, atomic move-to-default plus delete, including archived categories. Lock source/destination groups in ID order, recheck name conflicts, preserve category IDs and financial references, and refuse ambiguous merges. Keep compact cards with visible category previews, explicit organization controls and edit/delete actions; use isDefault for the default badge and protections rather than inferring it from display names.

- The user requested automatic sign-based cash-flow classification to remove hundreds of repetitive manual choices. Apply editable income/expense defaults to account imports and legacy unclassified drafts, retaining established reserve-transfer recognition and explicit reviewed types. Persist normalized legacy types on confirmation; do not retroactively change ledger history or classify settlement-only reports financially.
- Distinguish a later statement's reconciliation gap from editable account opening. Keep strict financial balance checks, expose whether an account has any transaction history, and guide the user to earlier unfinished imports. Upload/history records are not confirmed ledger movements; never fabricate a balance adjustment or suggest rewriting an established opening position to cover a missing month.

- Reprocess normalized saved data separately from original-file extraction because originals are intentionally discarded. Keep it within Imports through a dedicated service using existing account/batch locks and transactions. Preserve matching reviews conservatively; optional explicit reset reapplies classification, including reserve transfers. Reject confirmed/reversed rewrites and require original hash for re-extraction. No parser plugin layer or file storage infrastructure is added.

- The user requested less chrome, default Geral first and custom color only for groups. Use group tabs and a single category list, with semantic type colors for category rows and no individual color control. Archive categories through DELETE rather than physically deleting referenced financial classifications; preserve existing ledger/plan references and use established archived_at semantics.

- Counterparty identity, source aliases and category rules are separate, scoped entities. Support exact descriptions and true store IDs; never repurpose a transaction SOURCE_ID as a merchant ID or reconcile operations by names. The user explicitly requested retroactive application: relation creation and category-rule changes update uncategorized/rule-managed history, preserving manual choices and immutable financial facts. Deactivation stops automation without losing history.
