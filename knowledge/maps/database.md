## Integrity and reporting
- Financial tables have `user_id` and `workspace_id`. Migration 002 adds `(user_id, workspace_id, id)` references and RLS requiring both transaction-local identities. Workspace rows use owner-only RLS. The Auth identity is the root owner.
- Existing records are backfilled into one default “Pessoal” workspace per owner. Listing workspaces provisions this default idempotently for new users. Categories and command receipt keys are unique within their workspace. Migration 002 passed local backfill/isolation tests; remote application is pending DNS connectivity.
- Signed `amount_minor` is exact integer storage with validated application/JSON safe bounds; map explicitly to the transport amount contract. Require compatible account currency; multi-currency aggregation is outside pilot scope.
- Source transaction dates use SQL `date`; audit/expiry/commit timestamps use `timestamptz`. Store an explicit opening position immediately before the account's first included date.
- Recorded balance is opening amount plus included, non-reversed movements from that position onward. Do not persist an independently editable current balance. Earlier-history imports need an explicit opening-position review.
- Income/expense totals exclude internal transfers, opening balances, reversed entries, and unconfirmed drafts. Unclassified movements remain visible for review and balance coverage.
- Index owned account/date/ID transaction lists, owned import state/expiry, source references for duplicate lookup, and idempotency keys. No unique index on `source_operation_id` alone.
- Constrain paired transfers to the same owner/currency and equal opposing amounts; services write both legs in one transaction and tests prove rollback/consistency. A single observed imported transfer remains explicitly unmatched.
- Reversal retains provenance and changes financial inclusion explicitly; all balance and summary queries must honor the same state rule. Archive accounts/categories that have referenced history.

## Security and lifecycle
- Admin credentials apply migrations; runtime credentials cannot own tables, bypass RLS, or change schema. Restrict browser Data API grants for business tables.
- RLS binds ownership to claims set from verified identity inside the API's current transaction. Test missing identity, cross-user references, direct runtime queries, and pooled connection reuse.
- Version migrations only in `supabase/migrations/`; no second migration runner or auto-migration on startup. Keep an empty-database reconstruction path.
- Preview draft contents expire and are cleaned up operationally; committed provenance remains for reconciliation and reversal. Original PDFs are not retained by default.
- Schema details, unique retry keys, concurrency locks, restore ID remapping and conflict behavior must be finalized with implementation tests before migration application.

## Migration and recovery implementation
Use the root `db:setup`/`db:migrate` commands. The explicit runner records filenames in `mywallet_migrations.applied`, with a database advisory lock and atomic migration registration. Do not mix this history with Supabase CLI `db push`; the CLI remains useful for linking and local platform tools. Migration SQL has one source directory.

JSON financial backup/restore operates within the selected workspace and preserves accounts, categories, active transactions and transfer groups with remapped IDs. It excludes raw PDFs, import/audit history and reversed entries; operational database backups are still needed for complete historical recovery. Export reads use a read-only repeatable-read snapshot. Expired draft cleanup is an explicit operational command.

## Default groups and deletion
202610230005_default_category_groups.sql adds is_default and a unique default per owner/workspace/type, backfills a fresh named default for both types in every existing workspace and makes category.group_id non-null. Existing user groups named Geral are preserved; the default uses a free name such as Geral (padrão). No category IDs, ledger amounts or budgets are rewritten. An AFTER INSERT workspace trigger provisions future defaults. It is SECURITY DEFINER because workspace creation has no active financial scope; it only inserts groups owned by the new workspace row, and direct runtime/PUBLIC execution is revoked. A protection trigger rejects default removal/unmarking/identity/name changes. An invoker trigger assigns legacy null category writes to the scoped default for rollout compatibility.

Runtime receives DELETE on category_groups, still constrained by RLS and default protection. The service locks source/default rows in stable ID order, checks all category names including archived ones, moves categories then deletes the custom group in one existing scoped transaction. Conflicts abort without merging/renaming or changing financial references. Backup v3 adds an optional isDefault flag and restores flagged groups by type into destination defaults; older null group references resolve to those defaults.
